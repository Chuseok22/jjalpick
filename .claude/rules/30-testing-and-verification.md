# Testing And Verification

## Test strategy

- 꼭 필요한 부분만 테스트한다. 핵심 도메인 로직(상태 전이, 즐겨찾기 한도 계산, 리비전 롤백, 멱등 처리 등)은 테스트를 먼저 쓴다(RED → GREEN → REFACTOR). 단순 CRUD, 매핑, 설정 클래스는 의무가 아니다. 전역 규칙(TDD 필수, 커버리지 80%)은 이 프로젝트에서 적용하지 않고 커버리지 게이트도 두지 않는다.
- 통합 테스트를 하지 않는다. 테스트는 DB 없이 도는 단위 테스트만 쓴다.
- BE: JUnit 6, Mockito. 서비스·도메인은 DB 없이 단위 테스트, 웹 계층(예외 처리기, 보안 설정, 시각 직렬화 같은 중앙 처리)은 DB가 필요 없는 `@WebMvcTest` 슬라이스 또는 `standaloneSetup`. Testcontainers, H2, DB가 필요한 `@SpringBootTest`는 쓰지 않는다.
- 중앙에서 처리하는 횡단 관심사(시각 직렬화, 에러 변환 등)는 중앙 구성 요소에 대해 한 번 테스트하고, 각 컨트롤러에서 반복해 테스트하지 않는다.
- Flyway 마이그레이션과 JPA 매핑, 동시성(잠금, unique 제약)은 자동 테스트가 없다. 로컬 DB 실기동(`ddl-auto: validate`)과 수동 확인으로 검증하고 보고서에 남긴다.
- 시간이 결과에 영향을 주면 고정된 `Clock`을 주입한다. `LayerDependencyTest`를 완화하거나 삭제하지 않는다.
- Desktop: Rust 로직은 단위 테스트를 쓰고 OS 어댑터는 fake로 대체한다. 실제 클립보드·포커스·붙여넣기는 자동으로 판정하지 않고, 실기기에서 수동 호환성 테스트를 하고 결과를 기록한다(OS/앱 버전, 복사 성공, 실제 삽입 여부, GIF 애니메이션 보존, 대체 수단, 지원 등급).
- React(Desktop, Website): 도메인 로직과 훅을 테스트하고 핵심 화면만 컴포넌트 테스트를 쓴다. 타입 검사와 lint는 항상 통과해야 한다.

## Commands

- 스캐폴딩 전이라 확정하지 않았다. 프로젝트를 만든 뒤 실제 명령으로 채운다.
- PR 전에 변경 범위에 해당하는 검증 명령을 통과시킨다.

## Evidence

- 완료 보고에는 실행한 명령과 실제 결과를 함께 적는다. 실행하지 못한 검증(로컬 DB 실기동, 수동 호출, 동시성, 실기기 호환성 등)은 못 했다고 명시한다.

## Failure handling

- 테스트가 실패하면 구현을 고친다. 테스트가 틀린 경우에만 테스트를 바꾼다.
- Mockito로 확인할 수 없는 동작(잠금, flush 순서, 제약)은 선언 확인 테스트나 실기동으로 보완하고 미검증이면 보고서에 적는다.
